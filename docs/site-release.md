# サイトの確認と公開

第一章の公開後は、変更をプレビューで確認してから本番へ反映する。公開先のID・URLは [config/site-targets.json](../config/site-targets.json) を正本とする。GitHubへのpushやPRマージだけでは、どちらのサイトも更新しない。

## 環境と依頼

| 項目 | preview | production |
| --- | --- | --- |
| 用途 | 変更箇所、第一章の通し進行、保存の確認 | 通常プレイ |
| 閲覧範囲 | 所有者限定で開始。確認者の追加は依頼時だけ | 現在の一般公開を維持 |
| テスト機能 | 通常は `ENABLE_TEST_TOOLS=true` | 未設定か `false` |
| 保存 | 専用ホストの端末保存、専用SiteのDB | 現在の端末保存とDBを維持 |

- 「プレビューへ反映」、宛先未指定の「反映して」、単独の `$starlit-publish` はプレビューまで。本番も更新するには「本番へ公開」など明示する。
- 基本順序は **PR作成 → 明示承認後にマージ → プレビューへ反映 → 動作確認 → 依頼済みなら本番へ公開**。公開依頼が先にあれば、検証通過後に再承認を求めない。
- Sitesのデプロイ操作は、選択したSiteの公開を更新する操作。このプロジェクトでは別のSiteを確認用として運用する。`current_preview_url` や開発サーバーを、保存・DBの独立した確認環境の代用にしない。
- プレビューを一般公開へ変えない。テスト機能を有効にすると、そのサイトを閲覧できる全員が利用できる。

## 初期登録と保存の分離

新しい確認用サイトの初期構築時だけ、既存チェックアウトとは別の登録用フォルダーを用意する。その `.openai/hosting.json` は論理バインディング `d1: "DB"`、`r2: null` を持ち、まだIDを持たない状態から登録する。返されたIDを同じmanifestへ即座に保存し、宛先一覧へ記録する。一度登録したら同じIDを再利用する。

プレビューと本番のホスト名が異なることで、localStorageの保存領域を分離する。クラウドもSiteごとに管理される独立したD1を使う。同じ論理バインディング名 `DB` は使うが、本番DBへの接続設定やデータをプレビューへコピーしない。初回配置時にSitesのDB情報と、架空の確認用記録によるバックアップ・復元を確認する。

確認に本番の記録が必要な場合も、ユーザーが提供したコピーをプレビューへ別記録として読み込む。本番の端末保存を初期化・置換しない。プレビューで調整した記録を本番へ戻すことを通常手順に含めない。

## 公開用チェックアウト

GitHubの `.openai/hosting.json` は本番のまま保持する。Sitesのmanifestは一つのSiteだけを識別するため、プレビュー配信時には **manifestの `project_id` だけを変更した配信用コミット** を作る。

- `sourceCommit`: 確認対象となるGitHubのマージ済みソースSHA。両環境で共通。
- `deliveryCommit`: 対象Siteに実際にpushし、ビルド・梱包・保存する完全なSHA。サイト設定の差により `sourceCommit` と異なり得る。
- Sitesの保存APIの `commit_sha` には必ず `deliveryCommit` を渡す。元ソースのSHAを代入しない。配信用の変更をGitHubの `main` へpushしない。

公開タスクは次の手順を使う。資格情報・ビルド・梱包・保存APIの細部はインストール済みのSitesスキルを参照する。

1. GitHubをfetchして同期済み `main` のSHAを固定する。公開中の別タスク、共有チェックアウトの差分、対象Siteの既存バージョン・公開状態を確認する。公開処理を重ねない。
2. 宛先ごとの独立した配信用チェックアウトを用意する。共有の開発チェックアウトでmanifestを切り替えない。新規フォルダーの作成と既存の再利用を区別し、作業が残るものは使わない。
3. 対象Siteの専用Git remoteを、同じIDについて返された資格情報・URLから取得する。初回でremoteが空なら `sourceCommit` から始める。既存のSiteではremoteの最新HEADを親にして配信用ブランチを作り、空の作業状態で `git restore --source=<sourceCommit> --staged --worktree -- .` により追跡ファイルを元ソースと一致させる。GitHubのソースオブジェクトは事前にfetchしておく。これにより次のSitesへのpushもfast-forwardになる。
4. 配信用manifestの `project_id` だけを宛先一覧の値へ置換し、配信用コミットを作る。その他のソース差分、無関係な未追跡ファイル、資格情報、セーブを含めない。コミット本文に `Source-Commit: <完全なSHA>` と `Site-Target: preview|production` を残す。初回本番など差分がない場合は既存コミットを再利用してよい。
5. 最新のSites情報から下記の観測JSONを作り、公開前検査を実行する。プレビュー確認後にGitHubが進んでも、検査済みの `sourceCommit` を無言で置き換えない。新しいSHAを選ぶ場合は確認をやり直す。
6. 配信用チェックアウトの実行プロファイルを設定し、必要な依存関係を用意してビルドする。manifestが変わったら以前の別環境の成果物を再利用しない。build後も差分検査を行う。配信用コミットを対象Siteのremote branchへpushし、同じコミットの成果物を梱包・保存・デプロイする。force pushしない。
7. `succeeded`、返されたURL、配信用SHAを確認して記録する。Sitesの環境変数変更は保存済みの同じバージョンを再デプロイして反映する。更新したrevisionと実際の画面の両方を確認する。

環境の実行時値はSitesで管理し、manifestへ追加しない。本番は未設定か `false` のままにする。テスト機能の詳しい仕様は [開発と運用](development.md#テスト機能の環境設定) を参照する。

## 公開前検査と確認記録

正本のチェックアウトで宛先の整合を検査する。

```text
node scripts/check-site-release.mjs --config
```

配信用チェックアウトから、対象ソースに含まれるスクリプトで検査する。JSONはチェックアウト外か無視対象の `work/` に保存し、資格情報・セーブ・他の環境変数を入れない。

```text
node scripts/check-site-release.mjs preview <sourceCommit> work/observed.json
node scripts/check-site-release.mjs production <sourceCommit> work/observed.json
```

観測値の形は [site-observation.json](templates/site-observation.json)。これは未確認のひな型であり、そのまま本番検査に通らない。Sitesの `get_site`、`get_environment_variables`、バージョンと公開状態の取得結果から対象項目だけを転記する。

- `site.url`: 配置済みなら返された公開URL、初回だけ登録時に返された予定URL。宛先一覧から観測結果を捏造しない。
- `environment.testTools`: 実際の値が文字列 `true` なら `"true"`、未設定または文字列 `false` なら `null`。不明・秘密化された値・その他の文字列を無効と決めつけない。
- `mode`: プレビューのテスト確認は `test`、プレビューの通常モード確認と本番は `normal`。
- `previewVerification`: 本番公開時に必要。同じソースのテストモード・通常モードの公開ID、環境revision、第一章・保存復元・変更箇所の結果を記録する。
- `realDevice`: ブラウザーの画面幅確認と実機を区別する。未実施は `not-run` と理由を残し、成功とは報告しない。既知の実機不具合がある場合は本番公開を止める。

検査は、宛先の取り違え、テスト機能を有効にした本番配置、別SHAや未完了の確認記録、manifest以外の配信差分を拒否する。JSONの記載が事実かどうかを外部照合する機能ではない。公開タスクが取得元と画面確認の証拠を照合する。公開直前に宛先・環境revisionが変わっていたら再取得・再検査する。

確認結果は該当PR・Issueまたは公開タスクに、日時、バージョン、`sourceCommit`、`deliveryCommit`、Site/version/deployment ID、環境revision、URL、使用端末・ブラウザー、各項目の結果、未実施事項、証拠へのリンクを残す。結果のJSONだけで画面確認済みと扱わない。前回の本番deploymentも控え、復旧時は保存済みバージョンを選び直す。DBやセーブは巻き戻さない。

## 第一章の確認表

これは公開済み第一章の回帰確認。新しいシナリオの採用事項を定める資料ではない。現行の進行条件は [第一章のゲーム実装](prologue-gameplay.md) と `lib/prologue.ts` を参照する。

### 通常記録での通し確認

プレビューの通常モードで「最初から遊ぶ」から確認専用の通常記録を追加する。既存記録は残す。達成数・レベル・所持金の調整を使わず進め、各ステージの結果を記録する。

| 範囲 | 操作と期待結果 |
| --- | --- |
| 起動・1-1 | タイトルから開始し、出発話→冒険→達成話を通る。途中で会話を閉じても意図せず出発しない |
| 1-2〜1-3 | 前の達成話を読了して次が解放される。1-3読了後にお店が現れ、購入・装備・バッグの内容が一致する |
| 1-4〜1-5 | 行先確定時の背景、出発・帰還、戦闘、達成話がつながる |
| 1-6 | 探索が最後まで進み、戦闘は発生しない。比較のスチルを拡大して戻れる |
| 1-7〜1-8 | 調査・戦闘・作業が進み、1-8の途中で背景が切り替わる。作業で不要な攻撃演出が出ない |
| 1-9・章末 | 再点灯のスチルと「第一部 完」まで読める。既存の行先の周回と回想ができ、後続章の未実装機能が解放されない |
| 初達成・再読 | 初達成時は達成話待ちで止まる。既読話の再読で報酬が重複せず、周回と帰還ができる |
| 会話・画像 | タップ・Enter/Spaceで進む。スクロールや画像拡大で会話が進まず、閉じる操作が画面外へ消えない |
| セーブ | 冒険中・帰還後の再読み込みで進行を保つ。記録切替、ファイルの別記録への復元、プレビューDBへのバックアップ・復元ができる |
| 復帰・複数タブ | 非表示から戻って留守中進行を反映する。別タブと同時書き込みせず、通信断でも端末で継続できる |

### テスト記録での部分確認

プレビューを `ENABLE_TEST_TOOLS=true` で再デプロイし、「セーブ・設定」から別のテスト記録を作る。通常記録に数値調整が出ないこと、テスト記録だけで変更できることを確認する。変更した戦闘・会話・解放境界はここで重点確認する。

現行の「序盤・中盤・全解放」は第一章の任意ステージへ移動する保証ではない。必要な段階まで進めた **確認専用記録** をファイル保管して使う。作成元のソースSHA、到達地点、通常/テストの別を記録し、適合しない古いコピーを使わない。テスト用の解放済み記録だけでは、順番どおりの解放確認を代替できない。

その後、同じソースのままフラグを `false` または未設定で再デプロイする。ページを再読み込みし、テスト用記録の作成ボタン・数値調整が消えること、通常記録と既存テスト記録を引き続き読み込めることを確認する。プレビューの確認が終わったら `true` に戻して再デプロイする。

### スマホと公開後

画面幅を変えたブラウザー確認では、小さい縦画面、横向き、文字拡大で主要操作と会話を確認する。別枠の実機確認では、iPhone/Androidのホーム画面起動、BGM・効果音、画面ロック・バックグラウンドからの復帰を記録する。実機に触れていない自動確認を実機成功としない。

本番公開後は既存の個人セーブを使わない新しいブラウザーセッションで、起動、主要画像・音素材の読み込み、テスト機能の非表示を短く確認する。本番でテスト用記録を作ったり、数値を書き換えたりしない。
