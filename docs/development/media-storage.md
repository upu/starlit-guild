# Sites付属R2への素材配信

画像・動画・音声はSitesが用意する `BUCKET` に保存する。外部Cloudflareアカウント、公開バケット、独自ドメインは不要。ブラウザーは既存の同一オリジンのパスを使い、Sitesの閲覧制限を通ってサーバーから素材を受け取る。端末セーブ・DB・ゲームURLは変更しない。

## ビルドと版の対応

`scripts/media-manifest.mjs` のディレクトリ一覧を分離対象の正本とする。`build/media-assets.ts` は素材のSHA-256・サイズ・形式を計算し、配備するサーバーへ一覧を埋め込む。アップロード用の同じ一覧は `.sites-runtime/media-manifest.json` に出力する。`public/` の原本を削除せず、ビルド用の小さなpublicディレクトリを `.sites-runtime/` に作る。開発サーバーは従来のローカル素材を使う。

R2キーは `media/<SHA-256>.<拡張子>`。同じ内容を再利用し、変更時は別キーへ保存する。古いキーを自動削除しないため、保存済みのサイト版へ戻すと対応する素材も戻る。各SiteのR2は独立しており、プレビューへの投入を本番への投入済みと扱わない。

`app/[...assetPath]/route.ts` はビルド時の一覧にあるパスだけを配信する。未登録パスは404、素材不足・保存形式不一致は503。GET/HEAD、単一Range、ETagの再検証に対応する。パス自体は版で変わらないため `private, no-cache` で再検証し、長期immutableキャッシュを付けない。

## 素材の投入

`/api/media-import` は `ASSET_UPLOAD_TOKEN` が未設定なら無効。32文字以上のランダム値をSitesのsecretとして設定し、適用のため既存版を再配備する。プレビューにはSitesのサービスアクセス用トークンも必要。両方ともメモリー内で扱い、Git・CLI引数・ログ・PRへ書かない。

`node scripts/upload-site-media.mjs preview` の標準入力へ、`projectId`・`uploadToken`・`serviceToken` を持つJSONを渡す。本番は引数を `production` にし、[公開手順](site-release.md)の本番最終承認後だけ実行する。URLは `config/site-targets.json` から取り、対象IDも照合する。リダイレクト先へ認証情報を送らない。

アップローダーは4並列でHEAD確認→不足分PUT→HEAD再確認を行う。PUTは1素材ずつストリームで保存し、R2側でSHA-256を照合する。許可された拡張子・内容ハッシュのキーのみ受け入れ、1ファイル64 MiBまで。原本や生成物がビルド後に変わったら停止する。途中失敗は再実行で継続できる。読み取り口は現在の版に登録済みの素材しか公開しないため、次の版の素材を先行投入できる。

通常の更新順は **新ソースをビルド→現在の版の投入APIから新素材を保存・検証→新しい版を配備→表示を確認**。投入後はsecretを削除し、同じ版を再配備して投入APIが404になることを確認する。環境revisionと素材件数・バイト数を配備記録へ残す。

初回のみ投入APIがまだ存在しない。所有者限定プレビューでは先に小さなR2対応版を配備して素材を投入するため、投入完了まで対象画像が表示されない時間がある。本番への初回移行は別途、現行版に投入APIとBUCKETだけを追加して先行投入する段階を準備する。素材不足の新しいゲームを先に本番へ配備しない。

## 検証

`node --test tests/media-storage.test.mjs` と、ビルド後の `node tests/media-storage.integration.mjs` を実行する。後者は隔離したローカルR2で不正認証・ハッシュ不一致・重複投入・画像の全体/部分取得・既存ページを検査する。配備物に対象ディレクトリが残っていないことも検査する。Sites上のR2初期作成・サービス認証・実表示はプレビュー配備後の別の確認であり、ローカル検査だけで成功扱いにしない。
