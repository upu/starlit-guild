# ドキュメントの管理

[資料案内](../README.md) → [開発・運用](README.md) → ドキュメントの管理

## 入口と詳細の分担

`docs/README.md` は分野を選ぶ入口、分野の `README.md` は目的別の案内、個別資料は仕様・設定・制作記録の本文を担当する。アートのように種類が多い分野は、背景画像・人物画像などの案内を挟む。

例：資料案内 → アート・音 → 背景画像 → 第一章1-7・1-8の制作記録。

- 個別の章や素材が増えても、最上位の目次へ直接追加しない。担当する分野・素材種別の案内を更新する。
- 共通の扱いは種類ごとの資料、長いプロンプトや場面固有の条件は個別記録へ置く。短い記録は種類ごとの資料内の節でもよい。
- 本文の正本は一つにする。関連する分野からはリンクで参照し、操作仕様を画像生成手順へ混ぜない。
- 各案内ページには担当範囲と読む順序を示す。新しい案内・個別資料には親の案内へ戻るリンクを付ける。

## 資料の区分

| 区分 | 扱い |
| --- | --- |
| 現行実装 | 現在のゲームの仕様。数値・条件の最終的な正はソースコード |
| 制作資料 | 世界観・人物・シナリオの正本。制作の核・採用済み・制作案・将来の種・未設定を区別する |
| 制作記録 | 素材を再現・修正するためのプロンプト、制作条件、採用結果と当時の確認記録 |
| 開発資料 | 実装構成、検証、公開などの手順 |

「実装済み」「未実装」などの進捗は [章ごとの実装仕様](../gameplay/README.md#章ごとの実装) だけで管理する。制作資料・人物資料へ書き写さない。資料だけを更新した場合はゲームの会話やクエストまで変更されたとは扱わない。

## 補助ファイルの置き場

| 置き場 | 管理方法 |
| --- | --- |
| `docs/characters/`・`relationships/`・`factions/` | 人物・関係性・組織で正本を分ける。人物の追加は [共通書式](../characters/_template.md) を使う |
| `docs/art-generation/` | 生成プロンプトと制作条件のJSON。対応するアート資料から案内する |
| `docs/story/game-script/` | [ゲーム内台本](../story/README.md#台本と場面の素材)。手編集せず `npm run script:export` で更新する |
| `docs/templates/` | 公開確認などの雛形。[公開前検査](site-release.md#公開前検査と確認記録) から使う |

ソースから書き出す資料は、`generated` のような作り方の区分ではなく読む分野の下へ専用ディレクトリを作って置き、手で書く資料と同じディレクトリに混ぜない。ディレクトリの案内（`README.md`）も生成し、自動生成であることを冒頭に示す。コードが読み込む生成データは `lib/generated/` など使う側に置く。

直下には資料案内・[共通ルール](../agent-rules.md)・[用語集](../glossary.md)・旧リンク向けの [キャラクター案内](../characters.md) を置く。旧案内へ設定本文は追加しない。

## 追加・移動時の確認

1. 既存資料の担当範囲に収まるなら、そこを更新する。独立した詳細が必要な場合は担当分野へ文書を作り、親の案内からリンクする。
2. ファイルや節を移すときは参照元を検索し、相対リンクと見出しへのリンクを確認する。旧URLを残す必要があれば、元の場所は移動先への案内にする。
3. 入口から新旧の資料へ辿れること、設定・プロンプト・確認結果が欠落していないこと、本文が複数の正本へ重複していないことを確認する。

変更履歴や一時的な不具合記録は目次へ積み上げず、Git履歴やIssueへ残す。バージョン単位の要約は [CHANGELOG.md](../../CHANGELOG.md) にまとめる。
