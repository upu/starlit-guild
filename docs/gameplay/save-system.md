# セーブシステム

現行ゲームの保存、バックアップ、復元、互換性をまとめる。保存形式を変更するときは、既存プレイヤーの記録を失わないことを最優先にする。

## 基本方針

進行の正本は端末の localStorage にある `starlit-guild-v4`。クラウドはバックアップであり、通常プレイ中の進行判定を通信成功へ依存させない。

約1秒ごと、主要操作時、ページを離れる際に端末へ保存する。非表示中は定期描画・保存・バックアップを休止し、復帰時に経過時間を精算する。

再開時の留守中進行は最大12時間分を端末で精算する。

## アクセスとアカウント

ゲームサイトは所有者向けの限定公開。サイト閲覧の認証とゲーム用アカウントは別で、ゲーム専用の登録・ログイン画面は設けない。

ソースと開発履歴はGitHubの非公開リポジトリで管理し、Sitesへ公開するときはSites専用Gitにも同じソースを保存する。公開手順は [開発と運用](../development/development.md) を参照する。

## クラウドバックアップ

ゲームを開いている間は約5分ごとに、Sitesが管理するD1データベースへスナップショットを送る。通信待ちのために出発や手助けを無効化しない。ゲームを閉じている間はクラウド送信しない。

Sitesの閲覧アカウントを取得できる場合は、そのIDでバックアップを分離する。認証情報を持たないローカル環境などでは、HttpOnlyのランダムCookieによるゲスト識別を使う。

バックアップはユーザーと端末ごとに分離し、古い通信で新しい保存を上書きしないよう連番で更新する。復元では元の記録を破壊せず、新しい記録として追加する。

## 記録スロット

「セーブ・設定」から、最初から遊ぶ記録とテスト用記録を追加・切替できる。最大12個。不要な記録は一覧から確認後に端末から削除でき、空いた枠へファイルやクラウドの記録を読み込める。最後に残った1件は削除できない。

削除対象が遊んでいる記録だった場合は、一覧で次に並ぶ記録（末尾なら直前の記録）へ切り替える。削除前に残したい記録をファイルへ保存できるよう、確認画面で案内する。削除は端末内の記録だけを対象とし、ファイルや既に保存されたクラウドバックアップを同時に消す操作にはしない。

テスト用記録の新規作成と、序盤・第1章クリア・全ステージや達成ステージ・レベル・所持金の調整は、[テスト機能の環境設定](../development/development.md#テスト機能の環境設定)で有効にしたサイトだけで利用できる。調整対象はテスト用記録だけとし、通常の冒険にテスト用の資源を混ぜない。

テスト用記録は必ず物語モードで作る。達成ステージには第一章と第二章の通し番号を指定し、その数だけ出発・達成・読了を済ませた状態にする（2-3まで含めるとミラが加入する）。上限は現在のステージ総数で、それを超える値を渡しても最後のステージで止まる。無効なサイトでも既存のテスト記録は削除せず、切替・プレイ・ファイル読み込み・クラウド復元を維持する。

記録を切り替えると、その記録の留守中進行を精算する。

第2章を試す場合は「記録」タブの「第2章・標準」「第2章・余裕あり」から、2-1の出発前のテスト記録を新しく作れる。ファイルは不要。どちらも通常の冒険と別スロットに保存し、作成時に元の記録を置き換えない。能力・装備・検証手順は [戦闘バランス](combat-balance.md#再現できるテスト開始データ) を参照。

## 従来記録の扱い

章立ての物語モードにする前の試作（従来モード）の記録は読み込まない。取り除いて残りを開く処理も持たないため、従来記録を含む端末の保存・セーブファイル・クラウドの記録は、読み取れない記録として扱う。端末の保存が読めない場合は元の記録を上書きせずにエラーを表示し、ファイルやクラウドの記録は読み取れないと表示する。v3形式も同じ。

新しい記録は今も任意フィールド `prologue: true` を保存する。現在の版は読み込みにこの印を使わないが、以前の版のゲームは印のない記録を従来記録として取り除く。新しい版で保存した記録を以前の版で開いても消えないように、書き込みだけを続ける。

## ファイル保存

ファイル保存は選択中の記録を含む。読み込み時は既存記録を直接上書きせず、別の記録として追加する。

ブラウザーのデータを消すと端末の保存は失われるため、必要に応じてクラウドバックアップまたはダウンロードしたファイルから復元する。

ホーム画面からの起動など、端末や起動方法によって保存領域が分かれる場合がある。ホーム画面への追加を案内するときは、事前のファイル保管と読み込み方法も併せて案内する。

## 複数タブ

複数タブでは期限付きの端末内リースを使い、書き込みを1タブに絞る。「このタブで続ける」で書き込み権を引き継げる。

非表示から復帰したタブは、別タブが進めた記録を取り込んでから書き込みを再開する。

## バージョン移行

複数敵の戦闘では任意の `Run.enemies` に個別HPと行動時刻を保存する。項目がない旧記録の進行中の地点は残りHPと旧計算を維持し、次の地点・出発・休憩後の再挑戦から切り替える。v4のまま読み込める。保存項目と検証の詳細は [戦闘バランス](combat-balance.md#保存と互換性) を参照する。

v4の隊には、最後に実際に出発したクエストを表す任意の `lastQuest` がある。待機背景の保持にだけ使い、解放条件や報酬を変更しない。次の出発時に更新し、再読では変更しない。旧記録で欠けている場合もそのまま読め、第一章では既存の達成記録から背景を選ぶ。旧記録で進行中だったクエストは、達成・中断時にその行き先を補って保持する。

独自に付けた隊名は任意の `customName` に保存する。フィールドがない旧記録や名前を空に戻した隊は、現在のメンバーから表示名を生成する。従来の必須 `name` は旧記録との互換性のため保持し、新しい表示名の正本にはしない。

### v1〜v3（削除済み）

v1・v2・v3の形式と、その移行コード、旧サーバーAPI `/api/game` は削除した。読み込めるのはv4だけで、v1〜v3の記録はすべて[従来記録](#従来記録の扱い)にあたるため読み込めない。判定の経緯は [移行コードを削除してよいかの判断](#移行コードを削除してよいかの判断) を参照する。

### 追加フィールド

現行v4では、機能追加に伴うデータを可能な範囲で任意フィールドとして追加し、古い記録を読み込めるようにする。

装備は任意の `inventory` に保存する。`items` は装備品IDごとの総所持数（装備中を含む）、`equipped` は人物IDごとの武器・防具ID。同じ記録の全パーティで共用し、所持金は既存の `gold` を使う。装備追加前の記録では初期装備（弓・剣は討伐＋1、旅の服は護衛＋1）として解釈し、購入・付け替え時に保存する。ミラ加入時は使い慣れた杖と旅の服を追加して装備し、加入済みで杖を未所持の旧記録にも読み込み時に一度だけ補う。既存の装備枠は上書きしない。杖の所持を付与済みの印とし、外して保存しても再付与・再装備しない。形式はv4のままで、旧記録の資源・進行・HPを変更しない。取り込み時には未知の品・負数・端数・未加入者の装備・適性違い・所持数を超える同時装備を拒否する。

物語の預かり品・苔灯・標本は `story.read` と `story.departed` から導出し、個数を重複保存しない。`story` が存在しない旧記録は `done` を参照する。受け渡しや発見は初回読了で進み、周回や再読で再取得しない。お店の解放も第一章では既存のステージ解放条件を使う。

物語では `story` に、ふたりで出発・達成した依頼や読了した話を記録する。追加前の記録では、達成済み依頼の物語を読み返せるように引き継ぎ、起動時の強制再生は行わない。

従来モード専用のフィールド（`recruitment`、`wood` / `town` / `camp`、`gear`、`discoveries`、`claimed` / `lastDaily` / `receipts`、`run.detour` / `run.cheer` など）は保存形式から外した。読み込み時は未知のフィールドとして読み飛ばすため、これらを持つ物語モードの記録もそのまま開ける。

隊は1つだけになったため、`squads` は `party-1` のちょうど1件を受け付ける。

## D1 / Drizzle

`game_device_backups` を端末別バックアップに使う。旧 `game_saves` と `game_save_backups` は読む経路が無くなったが、テーブルは残している（[移行コードを削除してよいかの判断](#移行コードを削除してよいかの判断)）。

適用済みのDrizzleマイグレーションは変更せず、新しい変更は追加マイグレーションとして作成する。

## 移行コードを削除してよいかの判断

古い保存形式の移行コードは、次の2つがどちらも言える状態になったら削除してよい。実際に残っている記録の件数ではなく、**コードから到達できるか**で判断する。データベースに古い行が残っていても、読む経路がなければ影響しない。

1. その形式の記録を読み込む経路が、アプリ・API・ファイル読み込み・クラウド復元のどこにも無い。
2. その形式の記録を読み込めたとしても、結果が使われない（例：読み込んだ直後に取り除かれる）。

### 確認の手順

```bash
# 1. その形式のモジュールを参照している箇所を洗い出す
grep -rn "game-v1\|game-v2\|game-v3" lib app tests scripts

# 2. 旧APIを呼ぶコードが無いことを確かめる
grep -rn "api/game" lib app tests scripts

# 3. 削除して、型検査・lint・全テスト・ビルドが通ることを確かめる
npx tsc --noEmit && npm run lint && node --test tests/*.test.mjs && npm run build
```

参照が残っていても、それが移行コード自身の内部参照やテストだけなら、対象は到達不能と判断してよい。判断できない参照があるうちは削除しない。

### v1〜v3の判定（2026-09）

上の条件を両方とも満たしたため削除した。根拠は次のとおり。

- `/api/game` を呼ぶコードがアプリ側に1箇所も無かった。現行の進行は端末保存が正本で、このAPIは使っていない。
- `/api/backup` が返していた `legacy`（旧 `game_saves` の内容）は、[従来記録の扱い](#従来記録の扱い)で取り込みをやめたため、クライアントが読まなくなっていた。
- `migrate()` のv1〜v3経路は `version !== 4` のときだけ通るが、その結果には `prologue` が無いので、取り除きで必ず捨てられる。v3形式のファイル読み込みも同じく必ず新しい記録になる。つまり「移行して、直後に捨てる」だけの経路だった。

`game_saves` と `game_save_backups` のテーブル自体は残す。読む経路は無いが、削除するマイグレーションを足す利点が無いため。

## 変更時の原則

- 既存の端末保存を正本として扱い、確認やテストのためにユーザーのセーブを初期化・置換しない。
- 新しい機能は、可能なら旧データに存在しなくても解釈できる任意フィールドとして追加する。
- 復元や読み込みは、元の記録を残す方向を優先する。
- オフライン進行や通常操作を、バックアップ通信の成功条件へ結びつけない。
- 移行コードを削除する場合は、[移行コードを削除してよいかの判断](#移行コードを削除してよいかの判断)の条件と手順で確認する。

端末の時計を使う個人向けゲームであり、競争用の不正対策は目的に含めない。

## 横スクロール進行の互換性（v0.3.1）

新規出発では任意項目 `Run.road` に各人物・敵の位置、向き、歩行、ノックバック、カメラ位置、進行時計、作業中に襲撃した区間を保存する。既存のv4記録には補完しない。進行中の冒険のHP・残り作業量・時計・獲得済み報酬を保ち、その冒険の終了または帰還後の新規出発から横スクロールの進行処理へ移る。

作業中の襲撃は次の戦闘区間を前倒ししたもの。作業量と敵HPを別々に持ち、両方を完了したときに元の区間分の報酬を一度だけ精算する。保存検査は味方・敵と位置の対応、有限の座標、時刻の前後関係、襲撃区間の隣接関係を確認する。オフライン上限で時刻を移す際は移動時計も同じ量だけ移す。描画時の補間は保存や報酬処理を変更しない。
