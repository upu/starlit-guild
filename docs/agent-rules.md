# エージェント共通ルール

このファイルは作業ツールに依存しないルールの正本。Codex は [AGENTS.md](../AGENTS.md)、Claude Code は [CLAUDE.md](../CLAUDE.md) を入口として参照する。

版の判定とコード品質は [開発と運用](development/development.md#prごとのゲームバージョン)、公開の準備・検査・最終確認は [サイトの確認と公開](development/site-release.md) が詳細の正本。ツール固有の操作は各入口から参照する。条件を更新するときは担当する正本を直し、入口には要約と参照だけを置く。

## 作業と版

- GitHub の `main` を正本とし、作業前に別タスクの進行、worktree と未確定差分を確認する。作業中のファイルや無関係な変更を失わせない。
- 作業ブランチには `<agent>/<短い名前>` を推奨する。使用するエージェント名や既存のチーム規約に合わせる。
- PRではゲーム本体への影響を `game-change` / `no-game-change` のどちらかに分類する。[版の判定と変更履歴](development/development.md#prごとのゲームバージョン) に従い、通常はゲーム変更でパッチ版を上げ、それ以外は据え置く。章の区切りでは [マイナー版の条件](development/development.md#マイナー版を上げる契機) も確認する。
- セーブの正本は既存の端末保存。確認のためにユーザーのセーブを初期化・置換しない。

## 公開先

- 公開先は [site-targets.json](../config/site-targets.json) の `preview` / `production` で区別する。宛先未指定の反映依頼と、ゲームバージョンを上げた実装依頼はプレビューまで。ゲームバージョン据え置きの実装依頼では、明示的な反映依頼がない限りプレビュー反映を省略してよい。本番は実行時の明示指定に加え、同じソースのプレビュー確認と配備準備を終えた後の最終承認が必要。PRマージ承認とは分ける。
- 本番向けの準備と承認の手順は [本番配備の最終確認](development/site-release.md#本番配備の最終確認) に従う。開始時の本番指定やPRマージ承認を、配備承認へ流用しない。
- `.openai/hosting.json` は既存本番の識別子を維持する。プレビュー配信では独立した公開用チェックアウトで宛先を選び、[公開前検査](development/site-release.md#公開前検査と確認記録)を通す。本番のURL・DB・閲覧範囲と端末セーブを維持する。詳しくは [サイトの確認と公開](development/site-release.md)。
- ユーザーの宛先・ローカルのみ・PR作成まで・配備しない指定を優先し、調査・相談・レビューだけでは配備しない。

## 戦闘・育成・章のバランス

1. 先に [章ごとの戦力と到達時間](gameplay/progression-balance.md) を読み、対象章と前後の章の開始・終了条件、時間の目標、未設定事項を確認する。
2. 同資料から [戦闘の計算と調整手順](gameplay/combat-balance.md)、対象のテスト開始データ・自動シミュレーションへ進む。Lvだけで戦力を決めず、経験値・装備・技・加入状況を引き継ぐ。
3. 調整後は対象章の測定結果と次章の開始条件を一緒に更新する。新章の目標が未設定なら提案と確定を区別し、前章終了データから通しで検証する。目標をテスト結果に合わせて勝手に緩めない。
4. 時間は自動シミュレーション上の経過時間と人が遊んだ実測を区別し、追加育成・章全体・通算の内訳を記録する。自動検証だけで実機の体感確認済みとは報告しない。
5. 章の追加・標準クリア戦力や装備の調整時は、ゲーム内のテスト開始データも更新する。`scripts/generate-test-presets.mjs` へ新章の通し試走を追加し、`npm run presets:generate` で再生成する。必要に応じて `npm run presets:check` で確認し、通し試走による検査を毎回のCIへ追加しない。標準データは前章終了状態を引き継ぎ、「強くて最初から」は十分なレベルと資金だけを付与する。作成済みのテスト記録は自動で書き換えない。

## 世界観・人物・シナリオ

1. [資料案内](README.md)、[用語集](glossary.md)、[世界観](story/world-and-story.md)、[執筆指針](story/story-writing.md) を確認する。章・ステージ・クエストID・シーンIDの対応は用語集を使い、資料ごとに呼び名を作らない。
2. [キャラクター一覧](characters/README.md) で登場人物の名前・別名・IDを確認し、該当する `docs/characters/<キャラID>.md` を読む。
3. 個別ファイルから関係性・所属組織をたどる。アリアとレオンは [二人の関係性](relationships/aria-leon.md)、メリルとプティは [マッドハロウィン](factions/mad-halloween.md) も読む。
4. 対象プロットと、個別資料が案内する既存シーン・プロフィールを読む。第一章は [第一章プロット](story/story-part-1.md) を確認し、現行の加入順や来客シーンを新しい第一章の確定事項にしない。
5. 制作の核・採用済み・人物を深める軸・制作案・未設定を区別する。実装していない案を、ゲーム内で起きた出来事として扱わない。矛盾があれば、現在の依頼と資料の区分を確認し、推測で混ぜない。

個人設定は個人ファイル、共通の関係性は `docs/relationships/`、組織は `docs/factions/` を更新する。同じ本文を複数の正本へコピーしない。「実装済み」「未実装」の進捗は章ごとの実装仕様（[第二章のゲーム実装](gameplay/chapter-two-gameplay.md#実装状況) など）だけで更新し、制作資料・人物資料へ書き写さない。新しい人物には [共通書式](characters/_template.md) を使い、一覧と関連リンクを更新する。旧 `docs/characters.md` は互換案内であり、設定本文は追加しない。

資料のみの整理ではゲームコード・シーンID・セーブ形式を変えず、リンクと設定の欠落・区分を確認する。シナリオ実装を依頼された場合は、資料更新とは分けて実装・検証・報告する。
