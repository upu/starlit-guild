# STARLIT-GUILD の実装とプレビュー反映

共通ルールは [エージェント共通ルール](../../../docs/agent-rules.md)。このスキルは Codex の GitHub・PR 操作手順を定める。他のエージェントは共通ルールと自分の実行環境に合う手段を使う。

実装依頼では、GitHubの `origin/main` を正本としてPR作成まで自律的に進める。最新のPR状態と検証結果を提示してマージ承認を得た後は、後片付けと必要なプレビュー反映まで続ける。本番配備の最終承認は、PRのマージ承認と別に扱う。

## 反映先

反映の要否・宛先・依頼による制限は [共通ルールの公開先](../../../docs/agent-rules.md#公開先) に従う。単独の `$starlit-implement` も宛先未指定の実装依頼として扱う。必要なプレビュー反映への追加確認は不要。本番は実行時の明示指定に加え、[配備準備後の最終承認](../../../docs/development/site-release.md#本番配備の最終確認) が必要で、PRマージ承認を流用しない。

## 開始前

1. `git status`、現在のブランチ、worktree一覧、`origin` を確認する。別タスクの変更、未追跡ファイル、進行中の作業ブランチを失わせたり混ぜたりしない。
2. `git fetch origin --prune` でGitHubの状態を取得する。追跡ブランチの表示だけで最新と判断しない。
3. ローカルの `main` をチェックアウトしているworktreeを特定し、クリーンであることを確認してから `git pull --ff-only origin main` で同期する。未確定差分、競合、非fast-forwardで安全に同期できない場合は、reset、stash、強制操作をせず、そこで状況を報告する。
4. 同期済みの `main` から、目的が分かる作業ブランチを作る。共通の推奨形式は `<agent>/<短い名前>` で、Codex は `codex/<短い名前>` を使う。Codexの一時worktreeがdetached HEADなら、そのworktreeで同期済み `main` と同じコミットからブランチを作る。既存の同一タスク用ブランチを続行するときも、GitHubとの差分と用途を確認する。

## 実装からPRまで

- 依頼範囲だけを実装し、変更に応じたテスト、型検査、lint、ビルド、必要な画面確認を行う。既存セーブを初期化・置換しない。
- 会話の実装・修正は [台詞ごとの表情指定](../../../docs/story/story-writing.md#台詞ごとの表情指定) に従う。シナリオと掛け合いの各台詞に文脈に合う表情を明示し、対応する素材・値の受け渡し・実表示を確認してから完了とする。
- 舞台や移動を扱うシナリオでは、実装前に [fiction-atlas](../fiction-atlas/SKILL.md) を使って現状の位置関係を確認する。新しい場所・行路や地理設定の変更は、[地図とシナリオの照合手順](../../../docs/story/atlas/README.md#シナリオ作業での確認と更新) に従って根拠・地図データ・生成物まで同じPRで揃える。スキルの管理方針は [Codexの作業手順](../../../docs/development/codex.md) を参照する。地理に変更がなければ再生成は不要。
- 同期済み `main` を基準に [版の判定と変更履歴](../../../docs/development/development.md#prごとのゲームバージョン) を適用する。PR本文で `game-change` / `no-game-change` を一つ選び、章の区切りでは同資料の `minor-release` 条件も確認する。
- 差分と検証結果を確認し、意図したファイルだけをコミットする。force push、履歴の破壊、無関係な差分の取り込みはしない。
- 作業ブランチを `origin` へpushし、`main` 宛てのPRを作成する。PRテンプレートの `game-change` / `no-game-change` は分類に合わせてどちらか一方だけを選ぶ。pushとPR作成は、この個人リポジトリでは追加承認を求めずに進めてよい。Issueがある場合はPRから正しく参照する。
- PRのURL、変更内容、ローカル検証、GitHub checks、マージ可能状態を確認して報告する。失敗中・未完了のchecksを成功扱いしない。
- 反映先と、マージ後にプレビューへ進むか省略するかをPR報告に含める。Sitesへの配備を行う場合はマージと後片付け後に `starlit-publish` へ引き継ぎ、同じマージ済みソースを使う。呼び出し元が既に同じソースを配備中・配備済みなら、その処理を再利用して重複配備しない。

## マージ承認ゲート

- PR作成までの依頼、実装開始時の了承、以前の承認、または単なる公開依頼を、PRマージ承認として扱わない。
- PRと最新checksを提示した後、「マージして」「承認」「y」など、対象PRをマージしてよいことが分かるユーザーの返答を待つ。承認前はマージキュー投入も自動マージ設定も行わない。
- 承認後、対象PRのhead、差分、checks、レビュー、競合の有無を読み直す。状態が承認提示時から実質的に変わっていたり必須checkが失敗していたりする場合は、修正して再提示し、新しい承認を待つ。
- 状態が揃っていれば、リポジトリで許可された方式でPRをマージする。特段の指定や既存規約がなければ、1目的のPRはsquash mergeを使う。

## マージ後

1. GitHub上のPRがmergedで、merge commitが `origin/main` に含まれることを確認する。GitHubのリポジトリ設定による作業ブランチ自動削除も確認する。
2. `git fetch origin --prune` を行う。作業ブランチをチェックアウト中のworktreeは、未確定差分がないことを確認して `origin/main` のdetached HEADへ移すか、安全に別ブランチへ移す。
3. 今回のローカル作業ブランチだけを削除する。他タスクのブランチやworktreeは削除しない。削除できない場合は、保持理由と場所を報告する。
4. ローカルの `main` を `git pull --ff-only origin main` で同期する。最後に `main` と `origin/main` のコミット一致、作業ブランチのローカル・GitHub双方での不在、対象worktreeの状態を確認する。
5. [反映先](#反映先) の判断に従い、必要な場合は [starlit-publish](../starlit-publish/SKILL.md) へ同じマージ済みソースを引き継ぐ。本番の最終承認は配備準備後に別途待つ。

## 報告

PR作成時は、PRリンク、実装内容、検証結果、プレビュー反映の予定、マージ承認待ちであることを簡潔に伝える。マージ後は、PR、後片付けと `main` 同期、プレビューの配備結果・URLまたは省略した理由、未解決事項を伝える。本番向けの場合は、準備済みの内容を提示して最終確認し、承認後の配備結果を別に報告する。
