# STARLIT-GUILD の反映

短い公開依頼から、変更内容の確認、必要な修正・検証、履歴への保存、GitHub同期、現在の限定公開サイトの更新、成功確認まで進める。

## 対象と依頼の解釈

- 対象は STARLIT-GUILD。現在のチェックアウトの Git remote と `.openai/hosting.json` を読み、既存の GitHub `origin` と Sites を使う。別リポジトリでは自動適用しない。
- このプロジェクトの「反映して」と単独の `$starlit-publish` は、現在のタスクで合意した変更を GitHub と現在の限定公開 Sites の両方へ反映する依頼として扱う。具体的な宛先・内容の制限や「ローカルのみ」「資料のみ」は優先する。通常のコード編集・スキルの説明・状態確認は公開依頼ではない。
- 「ローカルにあるものを全部確定」は、その時点のゲームコード・利用素材・制作資料を対象にする。依存関係、キャッシュ、秘密情報、セーブ、生成途中の `outputs/`、公開作業用 `work/` を無差別に追加しない。既存の除外ファイルは削除しない。
- 資料の同期だけで物語をゲームへ実装した扱いにしない。シナリオ・クエストの実装が未依頼なら、残りとして明示する。

## 公開作業を重ねない

1. `git status`、差分、新規ファイル、ブランチ、remote を確認する。タスク管理機能があれば同じプロジェクトの動作中タスクを確認する。
2. 同じサイトの公開が進行中なら、その完了を確認して最新の内容を取り込む。完了していない公開を重複実行しない。権限なしに別タスクへ指示を送ったり停止したりしない。
3. GitHub と Sites の最新ソース、および Sites の保存・公開状態を読み直す。ローカルの追跡ブランチだけで最新と断定しない。
4. 今回だけの依頼では、他タスクの変更を混ぜない。必要なら独立した公開用チェックアウトを使う。全体確定の依頼では全対象を保存して統合する。reset、force push、未追跡ファイルの削除で合わせない。

## 検証と確定

- Sites の `sites-building` / `sites-hosting` を、その実行環境で利用できるインストール場所から読む。公開手順とツール仕様はそちらを正とし、このスキルに固定バージョンの認証・デプロイ実装を複製しない。
- 現在の実行プロファイルを設定してからビルドする。依存関係の変更があれば lockfile との整合を確認する。
- ゲームコードの変更では `node --test tests/*.test.mjs`、`node node_modules/typescript/bin/tsc --noEmit`、対象ソースの lint、公開ビルドを実行する。lint の例は `node node_modules/eslint/bin/eslint.js app lib tests scripts`。作業用チェックアウト・生成物を検査対象へ混ぜない。資料だけなら変更に応じて検証を省略できる。
- Windows の npm 起動や親フォルダー読み取りの制限による失敗を製品不具合と混同しない。npm ランチャーだけの問題なら、インストール済み Node.js の `npm-cli.js` を直接呼ぶ。権限が必要なら通常の承認機構を使い、制約を迂回しない。
- 表示・操作を変えた場合は、利用可能なブラウザーでローカル画面の該当操作を確認する。既存セーブを消さない。ブラウザー確認や実機確認ができなかった範囲は明記する。
- 不具合は原因に絞って修正し、関連する確認を再実行する。対象差分を履歴に保存し、公開するソースを固定する。remote が進んでいたら既存変更を保って統合し、内容が変わった場合は必要な確認とビルドをやり直す。

## GitHub と Sites の反映

- Git管理対象の変更は `starlit-implement` の手順で作業ブランチへpushし、`main` 宛てのPRにする。PRのchecksを提示した後の明示承認があるまでマージせず、`main` へ直接pushしない。保護解除やforce pushはしない。
- Sitesへの保存・公開は、そのPRがマージされ、同期済みのローカル `main` と `origin/main` が一致してから行う。PR作成までの依頼や公開依頼そのものをマージ承認として扱わない。
- Sites に同じソースを保存する。Sites のツールから取得した資格情報はコマンド単位で使い、ログ・ファイル・remote URLへ残さない。
- ビルド・梱包・Sites に保存するソースが同じコミットであることを確認する。梱包対象はビルド出力で、実際に使う画像・音・必要なマイグレーションも含める。
- push による自動公開が受理された場合は、その公開を確認する。そうでなければ Sites スキルに従って保存と公開を行う。タイムアウト時は同じコミットのバージョン・公開状態を確認してから再試行する。
- `succeeded` と公開URLを確認して完了とする。共有範囲を広げない。失敗が解決できなければ、GitHub保存とサイト公開のどこまで済んだかを分けて報告する。
- 最後にローカル差分と両remoteを再確認する。公開中に別タスクが新しく加えた変更は残し、今回公開した内容に含まれると報告しない。

## 完了報告

短い日本語で、反映内容、GitHubのリンク、成功したサイトURL、検証結果、未反映の残りを伝える。資料だけの更新と実際のゲーム変更を区別する。対象の確定差分が残っていなければその旨を書く。無視対象の作業ファイルがあることを未公開機能と混同しない。
